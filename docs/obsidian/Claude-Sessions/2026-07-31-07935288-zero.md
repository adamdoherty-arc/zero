## Shipped

**Zero — `430b315` (Fix-159, sprint 13230), 7 findings, all verified live:**

- **Stale credential, Zero alone.** freellmapi's unified key had been rotated; Legion, ADA
  and `shared-infra/.env` all carried the current one and **Zero's `.env` was the only
  stale copy**. `is_freellm_available()` returned `True` regardless because it checked only
  that a token was *set*, never that it *worked* — a probe that always passes. Rotated
  (verified: `routed_via=zhipu/glm-4.5-flash`, 200) and latched the tier off on 401/403 so
  a dead last line stops costing a round-trip on every call.
- **Self-amplifying 429s.** `structured_chat`'s retry exists to correct a model that
  returned prose instead of JSON. It caught *every* exception, so when no provider answered
  at all it re-traversed the whole chain twice more — tripling this call's own contribution
  to the 429 that caused its failure. **488 of the 622 failures were those amplified 429s.**
- **Chain-of-thought served as the answer.** The reasoning-for-empty-content substitution is
  deliberate (Qwen3-thinking/Kimi put the answer there), but `finish_reason=length` means
  the budget ran out *mid-thought*. Measured on gpt-oss-120b: `max_tokens=8` → `content=''`
  and `reasoning='The user asks: "Reply with exactly: OK"...'`; `max_tokens=300` →
  `content='OK'`. That first string was the user-visible reply. Fixed in **all three**
  extraction paths and pinned by a source-level test.
- **Unreadable failure records.** The durable `llm_usage.error_message` was written from
  `str(e)`, which is the empty string for every httpx transport exception — 132 of 622 rows
  recorded *that* a call failed but not *how*. The 2026-07-29 `_describe_exc` fix had been
  applied to the log line and not to the DB write beside it. Post-deploy: **0 empty rows.**
- **Readiness measured reachability, not capability.** Bifrost's `/health/liveliness`
  answers 200 in ~10ms whether or not any lane can complete, so the probe could not go red
  during a total outage of the thing it probed. Deliberately *not* fixed with a synthetic
  completion — the lane is single-slot and the outage was caused by queueing pressure, so a
  probe firing completions every 30s would add load exactly when it detects trouble. It now
  reads the outcome already observed on real traffic (the per-provider breaker), via a new
  side-effect-free `CircuitBreaker.peek_state` so an observer cannot consume the recovery
  slot it is measuring.
- **Robot residue** the 2026-07-11 deletion missed: `useReachyApi.ts` and
  `LiveCaptionsOverlay.tsx` were a closed pair referencing only each other, mounted nowhere,
  calling deleted endpoints. (`reachy_profiles/` stays — `soul_md` and `meeting_agent_service`
  read it.)

## Key Lesson

**A health probe must measure capability, not reachability — and the gap only shows up
during the outage the probe exists to catch.** Zero's readiness could not go red while 88%
of LLM calls failed for a day. The corollary matters as much: the fix must not add load to
the thing it watches. Reading an outcome already observed on real traffic is free and cannot
amplify; a synthetic completion every 30s would have made this outage worse.

Runner-up, self-inflicted: **for in-memory state, the process you measure must be the
process you changed.** My first verification opened a breaker inside `docker exec` and then
read readiness from the API process — separate registries. It only surfaced because
`get_primary_breaker_states()` returned an empty dict.
