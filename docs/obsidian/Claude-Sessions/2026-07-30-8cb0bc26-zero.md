## The incident, measured

07:12–08:09: ~60 consecutive Zero LLM failures against 2 successes, 23–126s latencies.
Meanwhile a **direct vLLM completion answered in 0.517s** and `generation_tokens_total`
advanced **~76 tok/s** throughout. vLLM was healthy; the block was queueing.

Mechanism: the `vllm-local` lane runs `concurrency=1` and carried a **600s** per-request
timeout with a **100-deep buffer**, behind `vllm-chat max_num_seqs=1`. One request could hold
the only slot for ten minutes while up to 100 queued behind it.

Demand on that 1-wide lane over 3h, from Bifrost's own `logs.db` — this is what redirected
the fix:

| virtual key | requests | avg | max | success |
|---|---|---|---|---|
| ada-prod | 4,101 (44%) | 6.1s | 78.8s | 4,029 |
| legion-prod | 3,175 (34%) | 0.3s | 27.5s | 3,145 |
| (none) | 1,643 | — | — | **0** |
| zero-prod | 461 (5%) | 3.3s | 19.8s | 459 |

**Zero was 5% of the load yet ~100% of the pain.** Bifrost logged 459/461 Zero successes
against Zero's own 67 recorded failures: the work completed *after* the client gave up.

Post-fix, 6 real calls through Zero's client: **6/6 success**. Calls 0–1 took 138.71s and
91.28s, the breaker went **OPEN**, and calls 2–5 took **0.13–0.34s**. The fallback could
always answer in ~0.2s — every call had simply been burning ~90–140s of primary timeouts
first.

## Key Lessons

- **When a health probe accuses a dependency, re-run the probe's exact request from a separate
  process before believing it.** `/health/ready` said `local_llm=unavailable legion=unavailable`;
  the identical GETs from a fresh process in the same container returned 200 in 0.03s. A 2s
  budget on a congested shared event loop measures the loop, not the dependency. This false
  signal misled the opening of this very run.
- **The app stalls were never the gateway.** `vault_reindex_tick` rescanned all 18,843 vault
  files every tick — 58.4s avg over 118 runs in 4h, a **48% duty cycle** of file I/O on the API
  event loop. It timed out `/health/live`, which is a bare `return {"alive": True}` with no I/O.
- **Green unit tests do not verify a DB write path.** My own first arm-append bound
  `json.dumps()` output to a JSONB param; the driver encodes a `str` as a JSON *scalar string*,
  so each arm element stored as text. `jsonb_array_length` still incremented so counts looked
  right and all tests passed — but every `ContentExperiment` validation then failed and
  `get_experiments` returned `[]`, blanking the whole API. Only the live end-to-end check
  caught it.
- **Treat a docstring feature claim as an assertion to verify.** "Circuit breaker per provider"
  was documented, absent, and unchallenged for the file's whole life.
- **Knowing when NOT to change shared infra is part of owning it.** `max_num_seqs=1` looks like
  an obvious mistune. The env history records 47+ wedge-restarts above 1 and, on 2026-07-14, a
  host GPU driver wedge that survived `wsl --shutdown` and needed a full reboot. Left at 1;
  fixed the queueing instead.
